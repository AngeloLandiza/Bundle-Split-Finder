# Step 7: the chip on Home Depot pages and the This page tab — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On a RYOBI or DEWALT bundle's Home Depot product page, show a chip under the price that says how the bundle splits and what it earns, read from the page and the saved data with no search, and open the side panel's This page tab on click.

**Architecture:** Core reads the product page (identifiers, price, Includes bullets) and turns it into a view using the same split, free matching and report code a scan uses. A content script reads the page it runs in, asks the worker for that view, and draws the chip in a shadow root. The worker remembers which bundle each tab shows; the panel's This page tab asks for the active tab's view.

**Tech Stack:** WXT 0.21 MV3 (content script UI via `createShadowRootUi`), React, plain CSS tokens, Vitest, Playwright e2e on `e2e/replay-server.ts`.

**Spec:** `docs/v1-plan.md` (Scope, Architecture, acceptance criterion 4), `docs/design.md` ("Chip on Home Depot product pages", Side panel tabs), mockup `docs/design/mockups/InPage.dc.html`, `docs/decisions.md`.

## Facts (checked Nov 17)

- Price block on product pages: `[data-component^="price:Price"]` (the attribute carries a version, e.g. `price:Price:v6.41.0`), seen on 328814689 and 320243741.
- The page's `window.__APOLLO_STATE__` holds `base-catalog-<itemId>` with `identifiers` (`brandName`, `modelNumber`, `productLabel`, `itemId`), `details.descriptiveAttributes` (the bullets), and a key starting `pricing(` whose object has `value` (price) and `original` (was-price): 328814689 value 189, original 338; 320243741 value 388, original 488. `bundleItems` and `bundleFlag` are null on bundles: Home Depot does not state the split. Shape sample: `.superpowers/sdd/2026-11-17-step-7-chip/evidence-pricing-2026-11-17.json`.
- The recorded page 328814689 (`fixtures/homedepot-pages/pages-2026-11-10.json`) has `identifiers` and `details` but no pricing; the replay server serves it at `/p/328814689`.
- WXT (wxt.dev, v0.21.5): `createShadowRootUi({ name, position: 'inline', anchor, append, onMount, onRemove })`, `cssInjectionMode: 'ui'` in `defineContentScript`; React mounts into a wrapper div created in `onMount`; `ui.autoMount()` mounts when the anchor appears; content scripts run only on full loads, so listen to `wxt:locationchange` for in-page navigation.
- Chrome (developer.chrome.com/docs/extensions/reference/api/sidePanel): `sidePanel.open` (Chrome 116+) "may only be called in response to a user action"; the gesture list includes "A user gesture on an extension page or content script". Whether a click relayed by `runtime.sendMessage` to the worker still counts is not documented: prove it in the owner's Chrome, and keep a fallback.

## Global Constraints

- CLAUDE.md in full. The chip and the This page tab never spend a search; Look up stays a separate, quoted action. Never guess: a split that is not certain shows "needs your answer".
- Every profit is labelled an estimate ("Est. profit" on the chip, as the mockup).
- Design: shadow root so page styles cannot reach it; 40px control placed directly under the price; white, 1px ink border, 6px radius, light shadow; never covers page content or moves layout by more than its own height; if the anchor is not found, do not inject. A setting turns it off. Tabs: Deals, This page, Review.
- Words: bundle, part, listing, search, scan, estimate; never "item" or "component" in UI copy.
- Tests on recorded or captured data; hand-made only where none exists, labelled. Each task runs typecheck, `npm test`, e2e.

## Review Focus

1. A product page that is not a bundle, or not RYOBI/DEWALT, or in a brand turned off in settings: no chip, nothing stored. (Task 1, Task 2.)
2. Visiting a page must not disturb a running or stopped scan job, nor overwrite an owner's answer, a Verify result, or a newer listing price. (Task 1.)
3. The price on the page differs from the stored listing price: the page's (it is what he sees) wins for the view, and the stored record keeps its own time. (Task 1.)
4. In-page navigation to another product without a reload: the chip follows the new page, never shows the old one. (Task 2.)
5. The side panel cannot be opened by the relayed click: the chip says so in one sentence instead of doing nothing. (Task 2.)

### Task 1 (Opus): core reads a product page and builds its view

**Files:** `core/src/hdPage.ts` (add `parseProductPage`), new `core/src/scan/pageView.ts`, tests `core/test/page-view.test.ts`. Reuse the runner's split and free-matching path; if it must be extracted to be shared, extract it (no second copy of the logic).

**Interfaces (produces):**
- `parseProductPage(text: string, itemId: string): ProductPage | null` with `ProductPage = { itemId; brand: string; model: string; title: string; price: number | null; wasPrice: number | null; bullets: string[]; description: string | null }`. `parseBundlePage` unchanged.
- `notePage(store: ScanStore, settings: ScanSettings, page: ProductPage, now: number): Promise<PageView>` where `PageView = { kind: 'none' } | { kind: 'bundle'; key: string; itemId: string; model: string; parts: number; row: BundleRow; lookupSearches: number }`. `kind: 'none'` when the brand is not in `settings.brands` or the model is not a bundle by `looksLikeBundle`. For a bundle: upsert its bundle record from the page (title, price, was-price, page content, seen time), split it and match its parts from saved listings exactly as a scan would (opening a split question when a scan would), never searching; build its `BundleRow` with the report's code; `lookupSearches` = what the panel's Look up would quote for its waiting parts (0 when none).

- [ ] Tests first: recorded 328814689 page text plus the captured pricing shape (labelled) → `kind 'bundle'`, model PBLRC2501SB, row parts PBLRC25B and PBLRC01B (acceptance 4), zero searches (a client that throws if called); with the replay's saved listings the row has the estimate a scan gives; a non-bundle and a brand turned off → `none`, store unchanged; Review Focus 2 and 3 as tests; a page seen twice does not duplicate questions.

### Task 2 (Sonnet): content script and chip

**Files:** new `extension/entrypoints/homedepot.content/` (index + Chip component + CSS), settings toggle in the options page and `extension/lib/prefs.ts` (`showChip: boolean`, default true), tests.

- Matches Home Depot product pages (`https://www.homedepot.com/p/*`) and, in the e2e build only, the replay server origin (follow how `__SPLIT_FINDER_BASE_URL__` is used).
- Reads `window.__APOLLO_STATE__` from the page's own script text, parses it with `parseProductPage` (core), sends `{ type: 'pageSeen', page }`; renders the reply. Anchor `[data-component^="price:Price"]`, `append: 'after'`, `autoMount`; no anchor → no chip. Re-runs on `wxt:locationchange` (Review Focus 4).
- Variants (copy from design.md and the mockup): estimate: "Splits into N parts", "Est. profit +$98.30", "ROI 52%", chevron; unknown prices: "Splits into N parts · Look up prices · N searches"; needs an answer: "Splits into N parts · needs your answer"; `none` → no chip. The whole chip is one `<button>`.
- Click: `{ type: 'openThisPage' }`; if the reply says the panel could not open, the chip shows under itself "Open Split Finder from the toolbar to see this bundle." (Review Focus 5).
- `showChip` false → no chip and no message sent.
- Tests: component variants; e2e on the replay page `/p/328814689`: chip under the anchor (the replay page needs a price block — add it to the replay server's page HTML for this id, as a recorded-shape element), no search used.

**Message contract (Task 3 owns the worker side):** `pageSeen { page: ProductPage }` → `PageView`; `openThisPage {}` → `{ opened: boolean }`.

### Task 3 (Sonnet, Opus review): worker wiring and the This page tab

**Files:** `extension/lib/worker.ts`, `extension/lib/messages.ts`, new `extension/entrypoints/sidepanel/ThisPageTab.tsx` (+ CSS), `Tabs.tsx`, `App.tsx`, tests.

- Worker: `pageSeen` → `notePage` (from Task 1) with the sender's tab id remembered (tab → item id, in `chrome.storage.session`); `openThisPage` → remember "show This page" for that tab, `chrome.sidePanel.open({ tabId })`, reply `{ opened }` (false if it throws); `getThisPage { tabId }` → the PageView for that tab's item, rebuilt from the store (no search).
- Tabs: Deals, This page, Review. This page shows, for the active tab: the mockup's view ("<MODEL> read from this page · no search used", headline estimate, "Costs $X · parts net $Y after fees", parts with grade, ASIN, price, net; "Open full detail" opening Detail; "Copy ASINs"); a bundle that needs an answer shows its Review question; no Home Depot bundle page in the active tab: "Open a Home Depot bundle page to see it here." It follows tab switches and page changes.
- The panel opens on This page when the worker says the chip opened it.
- Tests: worker handlers with fakes; tab states; e2e after Task 2 merges (controller).

### Task 4 (controller): merge, docs, QA, real-browser proof

Cherry-pick after the controller's own typecheck, tests and e2e; decisions.md; QA walkthrough; ui-reviewer on chip and tab screenshots; then the owner reloads the extension, opens 328814689 and a bundle page in his Chrome, clicks the chip (this proves or disproves the relayed `sidePanel.open`), and runs the step 6b check (scan, Accept all, Download CSV).
